# 11. 技術スタック推奨案

【事実】依頼者からの技術指定はない。選定基準は **① ランニングコスト最小化 ② 運用保守工数最小化 ③ インサイト非開示要件の実現しやすさ ④ 将来の iOS 展開** の 4 点である。

【仮定】本章の料金は 2026 年時点の一般的な公開価格を前提とした**概算**であり、実際の請求額を保証しない。**採用決定前に各サービスの最新価格を確認すること**（`OI-39`）。

---

## 11-1. 選定結果（サマリ）

| 領域 | 採用 | 主な理由 |
|---|---|---|
| モバイル | **Flutter** | 単一コードベースで Android／iOS／管理画面 Web をカバー。将来の iOS 展開コストが最小 |
| バックエンド／DB | **Supabase**（PostgreSQL） | **RLS とスキーマ権限でインサイト非開示を DB レベルで強制できる**。AND/OR 複合条件・集計・地理検索が SQL で完結 |
| バッチ | **pg_cron ＋ Edge Functions** | 追加サービス不要。コストゼロ、運用対象が増えない |
| 通知 | FCM | 無料枠が大きい（`OI-11`） |
| 状態管理 | Riverpod | Flutter で広く使われ、テストしやすい |
| ルーティング | go_router | 宣言的で、認証状態によるリダイレクトを扱いやすい |

## 11-2. バックエンド比較

### 11-2-1. 機能面の比較

| 観点 | Firebase | **Supabase** | AWS（Amplify / Lambda + RDS） |
|---|---|---|---|
| DB | Firestore（NoSQL） | **PostgreSQL** | DynamoDB / RDS |
| **インサイト非開示の強制** | △ セキュリティルールで制御。**「特定フィールドを絶対に返さない」の強制が難しく**、集計用の別コレクション設計が必要 | **◎ スキーマ分離＋GRANT で構造的に到達不能にできる。RLS でデフォルト拒否** | ○ RDS なら同等。ただし API 層を自作する必要がある |
| **AND/OR 複合条件検索** | **× Firestore は OR・複数範囲条件に強い制約**があり、条件式が複雑になるほど破綻する | **◎ SQL で自然に表現できる** | ○（RDS） |
| **集計（平均・中央値・ヒストグラム）** | × クライアント集計か Cloud Functions で自作 | **◎ SQL の集約関数・`percentile_cont` で完結** | ○（RDS） |
| 地理検索（距離・範囲） | △ GeoFirestore 等の外部ライブラリ | **◎ PostGIS / earthdistance** | ○ |
| スケジュール実行 | Cloud Scheduler + Functions | **pg_cron + Edge Functions** | EventBridge + Lambda |
| リアルタイム（チャット） | ◎ | ○ Realtime | △ 自作または AppSync |
| 認証 | ◎ | ○ | ○ |
| ストレージ | ◎ | ○ | ◎ |
| 学習コスト・初期構築 | ◎ 速い | ○ SQL の知識が必要 | △ 構築要素が多い |
| ベンダーロックイン | 高 | **低（素の PostgreSQL に移行できる）** | 中 |
| 運用工数 | 小 | **小** | 大 |

### 11-2-2. コスト比較（初期規模：ユーザー 300 人 / 案件 50 件/月 想定）

| 項目 | Firebase | **Supabase** | AWS |
|---|---|---|---|
| 無料枠での運用 | 可能（Spark プラン） | 可能（Free プラン） | 一部可能（無料枠の期限あり） |
| 無料枠の主な制限 | Cloud Functions の外部通信は従量課金プラン（Blaze）が必要 → **SNS API を叩く時点で Blaze 必須** | **プロジェクトが一定期間未使用で一時停止**。DB 500MB 程度 | 12 か月の初回無料枠、以降は課金 |
| 実質的な月額（概算） | 数百円〜数千円（読み取り回数に比例） | **0 円〜約 4,000 円**（Pro に上げた場合） | 約 5,000 円〜（RDS 常時稼働が効く） |
| コストが増える要因 | **ドキュメント読み取り回数**。案件一覧を全件読む設計だと急増 | DB サイズ・帯域 | RDS のインスタンス時間（**使わなくても課金**） |
| 数千ユーザー時の見通し | 読み取り課金が読みにくい | DB サイズ次第で予測しやすい | 予測しやすいが単価が高い |

### 11-2-3. 判定

【推奨】**Supabase を採用する。**

決定的な理由は 2 つ。

1. **インサイト非開示要件との適合性**。本アプリの中核制約は「特定のデータをクライアントに絶対到達させない」ことであり、これは PostgreSQL の**スキーマ単位の GRANT** で構造的に実現できる。Firestore のセキュリティルールは「どのドキュメントを読めるか」の制御であり、「このフィールドは絶対に返さない」を強制しにくい。
2. **条件マッチングと集計の要件**。AND/OR の任意ネスト条件、平均・中央値・ヒストグラム、地理検索——これらはすべて SQL の得意分野であり、Firestore では実装が破綻しやすい。

【事実】Firebase の弱点は「安いか高いか」ではなく、**本アプリの中核要件と設計思想が噛み合わない**点にある。

【推奨】ただし **FCM（プッシュ通知）だけは Firebase を併用**する。無料枠が大きく、Supabase 側に同等機能がないため。

## 11-3. モバイル技術比較

| 観点 | **Flutter** | React Native (Expo) | Kotlin Multiplatform | ネイティブ個別開発 |
|---|---|---|---|---|
| Android / iOS 共通化 | ◎ UI まで共通 | ◎ | ○ ロジックのみ共通、UI は個別 | × |
| 管理画面 Web の共通化 | ○ Flutter Web | ◎ React で自然 | × | × |
| 描画の一貫性 | ◎ 自前描画で OS 差が出にくい | △ OS 差が出る | ◎ ネイティブ UI | ◎ |
| グラフ描画（ヒストグラム） | ◎ `fl_chart` 等が充実 | ○ | ○ | ○ |
| Supabase 公式サポート | ◎ `supabase_flutter` | ◎ | △ | ○ |
| 学習コスト | ○ Dart の習得が必要 | ◎ TypeScript 人材が多い | △ | × |
| ビルド・リリースの手間 | ○ | △ Expo の制約に依存 | ○ | × 2 倍 |
| 将来の iOS 展開コスト | **最小** | 小 | 中 | 最大 |

【推奨】**Flutter を採用する。** 決め手は、初期 Android のみでも**同じコードがそのまま iOS になる**こと、および運営管理画面を Flutter Web で同一コードベースに載せられるため、**保守対象のリポジトリを 1 つに保てる**こと（`NFR-OPS-01`）。

## 11-5. リポジトリ構成（推奨）

```
/
├─ app/                     Flutter アプリ（Android / iOS / 管理画面 Web）
│  ├─ lib/
│  │  ├─ core/              共通基盤（認証・エラー・ロギング・DI）
│  │  ├─ features/          機能単位（feature-first）
│  │  │  ├─ auth/
│  │  │  ├─ sns_link/
│  │  │  ├─ campaign/
│  │  │  ├─ search/
│  │  │  ├─ application/
│  │  │  ├─ chat/
│  │  │  └─ report/
│  │  └─ shared/            共有ウィジェット・ユーティリティ
│  └─ test/
├─ supabase/
│  ├─ migrations/           DB マイグレーション（唯一の DB 変更手段）
│  ├─ functions/            Edge Functions（Deno / TypeScript）
│  └─ tests/                権限・RLS・k-匿名性の自動テスト
├─ docs/                    要件定義書・ADR・API 仕様
└─ .github/                 CI ワークフロー・Issue テンプレート
```

【推奨】**モノレポ**とする。アプリと DB スキーマの変更を同一 PR でレビューでき、非開示要件の違反を検知しやすいため。

## 11-6. 選定に伴うリスク

| リスク | 影響 | 緩和策 |
|---|---|---|
| Supabase Free プランはプロジェクト未使用時に一時停止される | 開発の中断、デモ時の障害 | 開発中は定期的にアクセスするか、早めに Pro へ移行 |
| Supabase の Edge Function には実行時間の上限がある | 日次バッチが完走しない | ディスパッチャ＋ワーカー方式でチャンク分割（9-7） |
| Flutter Web は管理画面用途では初回ロードが重い | 運営の使い勝手 | 初期は Supabase Studio で代替する案もある（`OI-15`） |
| Dart 人材の確保 | 開発体制 | GitHub Copilot 活用が前提のため影響は限定的 |
| BaaS へのロックイン | 将来の移行コスト | 素の PostgreSQL を使い、Supabase 固有機能への依存を最小化（RLS・RPC は標準機能） |
