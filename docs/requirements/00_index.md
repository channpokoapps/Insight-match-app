## 0-1. 本書の位置づけ

【事実】本書は、店舗・企業（PR依頼者）と SNS 投稿者をマッチングするモバイルアプリの要件定義書である。開発チーム（Claude Code 等の AI コーディング支援を用いた実装を想定）が、本書を読んだだけで実装に着手できる粒度を目標とする。

【前提】本書は「何を作るか（What）」と「なぜそう作るか（Why）」を定義する。「どう作るか（How）」の詳細実装は、本書を根拠に別途 ADR（`docs/adr/`）と実装で決定する。

## 0-3. 表記ルール（重要）

【事実】本書では、記述の確からしさを 4 種類のラベルで明示的に区別する。**ラベルのない断定的記述は本書には存在しない**ものとし、もし見つけた場合は誤りとして [open_issues.md](../open_issues.md) に起票すること。

| ラベル | 意味 | 扱い方 |
|---|---|---|
| **【事実】** | 外部仕様・法規制・依頼者から明示的に指定された要件など、検証可能で動かせないもの。 | そのまま実装の根拠にしてよい。ただし外部API仕様は変動するため、実装直前に一次情報を再確認する。 |
| **【前提】** | 依頼者との合意、または本プロジェクトが成立するために置いている条件。 | 崩れた場合、設計に大きな影響が出る。崩れた時点で本書を改訂する。 |
| **【推奨】** | 本書の作成者（アーキテクト）が提案する案。依頼者未指定の領域。 | 実装前に依頼者の承認が必要。承認されたら【前提】へ昇格させる。 |
| **【仮定】** | 情報が足りないため暫定的に置いた値・条件。 | 必ず [open_issues.md](../open_issues.md) に対応する `OI-xx` を持つ。 |

補助表記：

- **TBD**：未決定。必ず `OI-xx` を併記する。
- **要確認**：外部仕様の変動などにより、実装時点で一次情報の再確認が必要な箇所。

## 0-4. ID 採番規則

【推奨】本書および後続の実装・Issue で一貫して使用する ID 体系を以下に定める。

| 種別 | 書式 | 例 | 定義場所 |
|---|---|---|---|
| 機能要件 | `FR-{ドメイン}-{連番2桁}` | `FR-INS-03` | 5章 |
| 非機能要件 | `NFR-{カテゴリ}-{連番2桁}` | `NFR-SEC-01` | 10章 |
| 画面 | `SCR-{ロール}-{連番2桁}` | `SCR-CRE-04` | 6章 |
| ユースケース | `UC-{連番2桁}` | `UC-07` | 7章 |
| 未決事項 | `OI-{連番2桁}` | `OI-12` | [open_issues.md](../open_issues.md) |
| アーキテクチャ決定記録 | `ADR-{連番4桁}` | `ADR-0002` | `docs/adr/` |

## 0-5. 更新ルール

【事実】[../README.md](../README.md) に定義された既存ルールを踏襲する。

1. 各章の末尾に「本章の未決事項」節を置き、`OI-xx` の **ID とタイトルのみ**を列挙する。内容の本体は [open_issues.md](../open_issues.md) 側に記述し、二重管理しない。
2. 新しい用語を使う場合は必ず [glossary.md](../glossary.md) に追記する。用語の定義は用語集が唯一の定義元とする。
3. 図は Mermaid で記述し、画像ファイルは原則使用しない（差分レビュー可能性のため）。
4. 章をまたぐ参照は、章番号ではなく **ID**（`FR-xxx-nn` 等）で行う。章の挿入・並べ替えに強くするため。
