# 4. 前提条件・制約

【事実】本章は、設計の自由度を制限する外部要因を整理する。**特に 4-1 の SNS API 制約は、本アプリの成立可否そのものに関わる最重要制約**である。

---

## 4-1. 最重要の技術前提：インサイトデータの取得可否

### 4-1-1. 大原則

【事実】Instagram / TikTok / YouTube のインサイト（分析）データは、**投稿者本人の OAuth 認可（アカウント連携）があって初めて公式 API で取得できる**。第三者が他人のインサイトを本人の同意なく取得することは、各プラットフォームの利用規約上**不可**である。

【事実】したがって本アプリは、**「投稿者が SNS アカウントを連携（ログイン認可）することを必須」**とする設計を採る。連携していない投稿者は、案件に応募できない。

【事実】スクレイピング等による非公式な取得は、規約違反かつアカウント凍結リスクがあるため**採用しない**。

### 4-1-2. Instagram

| 項目 | 内容 |
|---|---|
| 使用 API | **Instagram Graph API**（【事実】2024年12月に Instagram Basic Display API は廃止済み） |
| 対象アカウント種別 | **ビジネスアカウント／クリエイターアカウント**のみ。個人アカウントではインサイトを取得できない |
| 前提条件 | Facebook ページとの連携が必要 |
| 認可方式 | OAuth 2.0（本人による認可） |
| 本番公開の条件 | **Meta のアプリ審査（App Review）が必須**。所要期間の目安は **2〜4 週間**（【事実】要確認：申請内容と時期により変動） |
| 取得可能なもの | 本人認可時のみ：インサイト（リーチ・インプレッション・保存数等）、オーディエンス属性（性別・年齢・地域） |
| 主な制約 | レート制限あり（目安：**200 リクエスト / ユーザー / 時**）。トークンは有効期限を持ち、失効時は再認可が必要 |

【前提】**投稿者はビジネス／クリエイターアカウントへの切り替えを行う必要がある**。個人アカウントのままでは本アプリを利用できない。この事実は、登録フローの最初に明示し、切り替え手順のガイドを用意する必要がある（登録離脱の主要因になりうる）。

### 4-1-3. TikTok

| 項目 | 内容 |
|---|---|
| 使用 API | **Login Kit / Display API**（公式） |
| 認可方式 | ユーザー OAuth 認可が前提 |
| 本番公開の条件 | TikTok for Developers のアプリ審査が必要（要確認） |
| 初期スコープ | 【前提】初期リリースでは対応しない（`OI-02`） |

### 4-1-4. YouTube

| 項目 | 内容 |
|---|---|
| 使用 API | **YouTube Data API v3** ＋ **YouTube Analytics API** |
| 認可方式 | 非公開データの取得には OAuth 2.0 必須 |
| 費用 | 無料 |
| 主な制約 | **1日あたり 10,000 クォータ単位**の上限（プロジェクト単位）。上限緩和には申請が必要 |
| 初期スコープ | 【前提】初期リリースでは対応しない（`OI-02`） |

### 4-1-5. プラットフォーム横断の比較

| 観点 | Instagram | TikTok | YouTube |
|---|---|---|---|
| 初期リリース対応 | **必須** | 将来 | 将来 |
| 本人認可の要否 | 必須 | 必須 | 必須（非公開データ） |
| 事前審査 | 必要（2〜4週間） | 必要（要確認） | 不要（クォータ緩和申請時のみ） |
| アカウント種別の制約 | ビジネス／クリエイターのみ | 要確認 | 特になし |
| 主なレート制限 | 200 req/ユーザー/時 | 要確認 | 10,000 quota/日（プロジェクト単位） |
| オーディエンス属性 | 取得可（本人認可時） | 要確認 | 取得可（本人認可時） |

> 各プラットフォームの取得可能指標の詳細対応表は **9章** に記載する。

### 4-1-6. 制約が開発計画に与える影響

【事実】Meta のアプリ審査に 2〜4 週間かかるため、**アプリ審査申請は開発工程のクリティカルパス**になる。

【推奨】以下の順序を推奨する。

1. 開発初期に Meta 開発者アカウント・アプリを作成し、**開発モード（テストユーザーのみ）で先行して実装・検証**する。
2. 審査に必要な要素（プライバシーポリシー URL、アプリの用途を説明するスクリーンキャスト、データ利用目的の説明）を、機能完成を待たずに準備する。
3. 中核機能が動く時点で審査申請し、**審査待ちの期間に残りの機能を実装**する。
4. 審査で差し戻された場合の再申請リードタイムをスケジュールに織り込む。

## 4-2. 法規制・ガイドライン上の制約

【事実】以下は日本国内でサービスを提供する場合に適用される。

> 注: 本節の `R-n` は法規制の通し番号であり、[AGENTS.md](../../AGENTS.md) §0 の開発ルール `R-1〜R-10` とは別物。同様に、4-4 の `T-n`（体制制約）は [backlog.md](../backlog.md) のタスク `T-xxx` と、4-5 の `E-n`（技術前提）は 12章の拡張余地 `E-n` と番号体系が独立している。

| # | 法規・ガイドライン | 制約内容 | 本アプリへの影響 |
|---|---|---|---|
| R-1 | **景品表示法（ステルスマーケティング規制、2023年10月施行）** | 事業者が広告であることを隠して第三者に投稿させる行為は不当表示にあたる | 案件で依頼する投稿には **`#PR` 等の明示が必須**。指定ハッシュタグに広告表記を強制的に含める設計とする（`OI-04`） |
| R-2 | **個人情報保護法** | 個人情報の取得目的の明示、第三者提供の制限、安全管理措置 | インサイト・オーディエンス属性は個人に関する情報として扱う。利用目的（マッチング条件判定・匿名集計）をプライバシーポリシーに明記し、同意を取得する |
| R-3 | **各 SNS のプラットフォームポリシー** | 取得したデータの保存期間・利用範囲・第三者提供の制限 | インサイトの保存期間・削除方針を定める（10章）。**連携解除時にはインサイトデータも削除**する |
| R-4 | **消費者庁ガイドライン（口コミ・体験談）** | 実体験に基づかない投稿の禁止 | 案件の必須投稿内容に「実際に体験した内容」の指示を含める |
| R-5 | **特定商取引法／資金決済法** | 【前提】初期は金銭のやり取りがないため直接の適用は限定的。将来の有償案件・アプリ内決済で影響 | 12章で設計方針を記載 |
| R-6 | **青少年保護（各社ストアポリシー含む）** | 未成年の取り扱い | 投稿者の年齢制限を定める必要（`OI-08`） |

【推奨】利用規約・プライバシーポリシーは**専門家のレビューを受ける**こと。特に「インサイトは PR依頼者に開示されない」という本アプリの中核的な約束は、プライバシーポリシーに明記すべきである（`OI-03`）。

## 4-7. 制約から導かれる設計方針（まとめ）

| 制約 | 導かれる設計方針 |
|---|---|
| インサイトは本人認可がないと取得できない | SNS 連携を投稿者の必須ステップとし、連携完了までは応募不可とする。連携率が KPI になる |
| Instagram はビジネス／クリエイターアカウント必須 | 登録フロー冒頭でアカウント種別を案内・判定し、切り替え手順をアプリ内ガイドとして提供する |
| トークンは失効しうる | 「要再認可」状態を明示的にモデル化し、失効検知 → 通知 → 再認可の導線を設計に含める（3章の状態遷移図） |
| レート制限がある | バッチをスロットリングし、指数バックオフ付きのリトライキューを持つ。全ユーザーを同時刻に処理しない |
| リアルタイム取得しない | 「最終更新日時」を投稿者・PR依頼者双方に明示し、数値が最大 24 時間前のものであることを UI で伝える |
| インサイト実数値は誰にも開示しない | スキーマ分離＋RPC＋k-匿名性の 3 層防御（2-4 参照）を全実装の絶対制約とする |
| ステマ規制 | 指定ハッシュタグに広告表記を必須で含める。案件作成 UI で強制する |
| ランニングコスト最小化 | サーバーレス／BaaS 中心。常時稼働サーバー・専用ステージング環境を初期は持たない |
| Meta 審査に 2〜4 週間 | 開発初期に開発者アカウントを準備し、審査申請をクリティカルパスとしてスケジュールに組み込む |
