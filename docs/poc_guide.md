# PoC の回し方ガイド（スマホだけで完結）

> **現在の状態（2026-08-13〜）**: 費用が発生しうるリソースを整理するため、Firebase / Google Cloud
> 向けの自動デプロイ・APK 配布のワークフローをリポジトリから削除した（詳細と再設定手順は
> [ADR-0007](adr/0007-pause-firebase-gcp.md)）。**新しい変更を PR プレビューや本番 Web 版に
> 反映する自動化、`/apk` での配布は現在使えない。** 既存の本番 Web 版 URL は、Firebase
> プロジェクト自体を削除するまでは閲覧できるが、それ以降は更新も閲覧もできなくなる。
> Issue → Claude が実装 → PR のループ自体は引き続き有効なので、PR の中身は GitHub 上の差分や
> ローカルでの `flutter test` / `supabase test db` で確認すること。

プログラミングの知識がなくても、**スマホと GitHub だけ**で
「アプリを触って気づく → Claude に直してもらう → 直った結果を確認する」
のループを回すための手順書。PC を開く必要は原則ない（例外は §3 の「サーバー側の変更」だけ）。

この仕組みの初回セットアップ（Secrets の登録など。管理者が PC で 1 回だけ行う）は
[manual_setup/github_automation.md](manual_setup/github_automation.md)。
このガイドは「操作する人」の視点だけで書く。

## 0. 最初に覚える言葉は 3 つだけ

| 言葉 | 意味 |
| --- | --- |
| **Issue（イシュー）** | 「ここを直してほしい」という依頼メモ。これを書くと Claude が動き出す |
| **PR（プルリクエスト）** | Claude が作った「変更の提案」。取り込む前に、中身を試せるプレビューが付く |
| **マージ** | 提案をアプリ本体に取り込む操作。ボタンを 1 回押すだけで、本番にも自動で反映される |

## 1. 事前準備（最初に 1 回だけ）

1. スマホに **GitHub モバイルアプリ**を入れて、このリポジトリ
   （`channpokoapps/Insight-match-app`）を開けるようにする
   （ブラウザでも可。ただしアプリの方が通知が届いて待ち時間に気づきやすい）
2. 本番の Web お試し版を**スマホのホーム画面に追加**しておく

   | アプリ | URL |
   | --- | --- |
   | Web お試し版（閲覧専用） | <https://insight-match-2fbaa.web.app> |

3. Android 実機で確認する人は **Firebase App Distribution のテスター登録**を済ませ、
   招待メールの案内どおりスマホに **App Tester** アプリをセットアップする
   （手順: [manual_setup/github_automation.md](manual_setup/github_automation.md) §5）

> **このアプリならではの注意。** Web お試し版は**閲覧専用**で、応募・チャット・
> SNS 連携などのアクションは Android アプリだけでできる。
> 「見た目の確認は Web プレビュー、操作の確認は APK」と使い分ける（§3）。

## 2. 基本ループ（これだけ回せばよい）

```
① スマホでアプリを触る（気になる点を見つける）
        ↓
② GitHub で Issue を書く → 最後の質問で「依頼する」を選ぶ
        ↓ （3〜15 分待つ）
③ PR が自動で立つ → テストとレビューが自動で走る
        ↓ （さらに 5〜10 分）
④ PR にプレビュー URL がコメントされる → スマホで開いて確認
        ↓ ダメなら @claude にコメントで追加指示（③に戻る）
⑤ よければマージ → 15〜25 分で本番に自動反映 → ①に戻って再確認
```

### ② Issue の書き方

1. リポジトリの **Issues → New issue** を開く
2. **「不具合の報告」か「改善したいこと」**を選ぶ
3. フォームを埋める。どの画面の話かは選択式なので、ファイル名や
   機能 ID を知らなくてもよい。**スクリーンショットを貼ると精度が上がる**
   （入力欄を長押し → 写真を添付できる）
4. 最後の **「Claude に実装を依頼しますか」で「依頼する」**を選んで送信

「いまは依頼しない」で記録だけ残し、あとから Issue に
`@claude 直して` とコメントして起動することもできる。

> **スクリーンショットの注意（重要）。** このリポジトリは**公開**されている。
> インサイトの実数値（フォロワー数・リーチなどの数字）、SNS のアカウント名、
> 氏名・メールアドレスが写った画像は貼らない。迷ったら塗りつぶす。
> 「実数値は誰にも見えない」がこのプロダクトの生命線（AGENTS.md R-1〜R-7）。

> **落とし穴が 2 つある。**
>
> 1. **GitHub モバイルアプリはフォーム非対応。** アプリから Issue を作ると
>    素の入力欄になり「依頼する」の選択肢が出ない。その場合は本文に自分で
>    `@claude` から始まる依頼文を書く（またはブラウザで GitHub を開いてフォームから作る）
> 2. **作成した後から本文に `@claude` を書き足しても起動しない。**
>    起動判定は「作成した瞬間」の本文で行われるため。書き忘れたら本文編集ではなく、
>    その Issue に `@claude 対応して` と**コメント**する

### ④ プレビューの確認

PR の画面を下にスクロールすると、bot が**確認用 URL** をコメントしている。
タップしてスマホで実際に触る。

直したいところがあれば、マージせずに PR へコメントする。

```
@claude 案件カードの報酬額が画面からはみ出してる。折り返して表示して。
```

数分待つと修正が積まれ、プレビューも自動で更新される。納得いくまで繰り返す。

> プレビュー URL は**全 PR 共通の固定 URL**（後勝ちで上書き）。複数の PR を
> 同時に進めているときは、コメントの「最後にデプロイした PR: #n」を見て、
> いま開いているプレビューがどの PR の内容かを確認する。

### ⑤ マージしてよいかの 4 点チェック

1. **チェックが全部緑（✓）か。** 赤（×）があれば
   `@claude CI が落ちてる。原因を調べて直して。` とコメントする
2. **Claude の自動レビューコメント**に重大な指摘が残っていないか。
   「⚠️ 自動レビューは実行できませんでした」というコメントが付いている場合は
   利用枠切れが典型。チェックはワーニング止まりでマージはできるが、
   レビューが無いぶん **Files changed の差分を自分の目で確認**する
3. **プレビューを自分のスマホで確認したか**（自動テストは見た目の崩れを検出できない）
4. **`supabase/` を変更した PR か**（PR の Files changed で分かる。bot のコメントにも
   警告が出る）。この場合はインサイト非開示のルール（R-1〜R-5）に触れる可能性が
   あるので、**急いでマージせず、レビューコメントをよく読む**

4 つ揃ったら **「Merge pull request」→「Confirm merge」** をタップ。
Web の変更はここから先は全自動。

## 3. どこで動作確認するか（変更の種類別）

| 変えたもの | マージ前（プレビュー） | マージ後（本番） |
| --- | --- | --- |
| 画面・見た目（`app/` の変更） | PR に自動でコメントされるプレビュー URL | ホーム画面に追加した URL |
| 応募・チャットなど Android だけの操作 | PR に **`/apk` とコメント**する → 8〜15 分でスマホの App Tester に通知が届く | `app/` に変更があれば自動で再配布される |
| サーバー側（DB・集計・インサイト同期など `supabase/` の変更） | **プレビュー不可**（PR コメントに警告が出る） | **手動反映が必要**（下記） |

> **サーバー側の変更は、マージしただけでは本番に出ていない。** 本番のデータベースを
> 書き換える操作なので、自動では反映しない（理由と再検討は
> [open_issues.md](open_issues.md) の `OI-45`）。マージ後の bot コメントの ⚠️ を
> 見落とさないこと。
>
> **DB（マイグレーション）はスマホから反映できる。**
> GitHub の **Actions → 「Supabase マイグレーション反映」→ Run workflow**。
>
> 1. まず**そのまま実行**する（既定は確認のみで、何も変更しない）。
>    実行結果の Summary に一覧が出る。**Remote 欄が空の行が未適用**。
> 2. 未適用があれば、`apply` にチェックを入れてもう一度実行する。
>
> Edge Functions（`supabase/functions/`）の反映だけは、まだ PC が必要:
>
> ```bash
> git pull
> supabase functions deploy        # Edge Functions（サーバー処理）を本番に反映
> ```
>
> **反映漏れの見分け方**: アプリの画面に
> 「アプリの更新がサーバー側にまだ反映されていません」と出たら、上の
> ①②（マイグレーション反映）をやっていないサイン。

## 4. 伝わる Issue の書き方のコツ

Claude への指示が曖昧だと、往復が増えて時間と利用枠を消費する。

| | 例 |
| --- | --- |
| ❌ 曖昧 | 「案件画面が使いにくい」 |
| ⭕ 具体的 | 「投稿者側の案件一覧で、条件に合わない案件もグレーで表示されている。合わない案件は最初から非表示にしてほしい」 |

- **1 つの Issue に 1 つのテーマ。** 複数詰め込むと PR が大きくなり、確認もマージ判断も難しくなる
- 「**どの画面で**・**何をしたら**・**何が起きたか**・**どうなってほしいか**」の 4 点が揃っていれば十分
- 不具合の報告には**再現手順**（タップした順番）を書く。フォームに欄がある
- 動作に関わる変更なら「**テストも書いて**」と添える
- **インサイトの見せ方に関わる要望は慎重に。** 「数値をもっと見せて」系の依頼は
  このプロダクトの大前提（実数値は誰にも見えない）と衝突する。Claude は
  非開示側に倒すよう指示されているので、「なぜ必要か」を書くと適切な代替案
  （バッジ表示・レンジ表示など）が返ってきやすい

## 5. 待ち時間の目安

「反応がない」と焦る前に、まずこの時間だけ待つ。

| 待っているもの | 目安 |
| --- | --- |
| Issue 作成 → Claude が PR を作る | 3〜15 分 |
| PR 作成 → テスト（CI）の結果が出る | 5〜10 分 |
| PR 作成 → プレビュー URL のコメント | 6〜10 分（Flutter Web のビルドに時間がかかる） |
| `/apk` コメント → スマホに APK の通知 | 8〜15 分（初回は 20〜25 分） |
| マージ → 本番反映 | 15〜25 分（CI の成功を待ってから始まるため） |

## 6. うまくいかないとき

| 症状 | まずやること |
| --- | --- |
| Issue を作ったのに Claude が動かない | 「依頼する」を選んだか確認。選び忘れたら Issue に `@claude 対応して` とコメントすれば起動する |
| プレビュー URL が来ない | 変更がサーバー側だけの可能性（§3 参照）。PR のコメントの警告を読む。「Secrets 未設定」と出ていたら管理者に [manual_setup/github_automation.md](manual_setup/github_automation.md) を渡す |
| プレビューでログインできない（Google でアカウントを選んでも進まない） | プレビュー URL のログイン許可登録が済んでいない。管理者向け手順: [manual_setup/github_automation.md](manual_setup/github_automation.md) §4（Firebase の「承認済みドメイン」にプレビュー URL を登録する） |
| APK の通知が来ない | `/apk` を **PR に**コメントしたか確認（Issue では動かない） |
| PR に「⚠️ 自動レビューは実行できませんでした」と出る | Claude の利用枠切れが典型。**マージ・デプロイは止まらない**（テストが緑なら可）。差分を自分の目で確認してからマージし、枠が回復したら PR に `@claude レビューして` とコメントすれば再実行できる |
| マージしたのに本番が変わらない | 25 分待つ。`supabase/` の変更なら反映（§3）がまだの可能性。それでも変わらなければ Issue で `@claude main のデプロイが失敗してないか調べて` と依頼する |
| 「アプリの更新がサーバー側にまだ反映されていません」と出る | DB のマイグレーションが未反映。§3 の「Supabase マイグレーション反映」を実行する |
| 案件を作ろうとすると「店舗情報を取得できませんでした」と出た（旧版） | 同上。DB 未反映が原因だった。現在は注意書きが出るだけで、そのまま案件を作成できる |
| 何をしても直らない | 新しい Issue に「〜を試したがこうなる」と経緯ごと書いて依頼し直す |

**壊すことを恐れなくてよい。** まだ本番の利用者はいない。壊れたらもう一度
Issue を書けば直せるし、テスト（CI）が失敗したコミットはそもそも本番に
出ない仕組みになっている。ただし **DB・インサイトまわり（`supabase/` の変更）
だけは §2-⑤ の 4 点チェックを丁寧に**。ここはこのプロダクトの生命線のため、
自動マージも設定していない（必ず人間がマージボタンを押す）。

## 7. 費用の感覚

- **GitHub Actions**（テスト・デプロイの実行時間）: このリポジトリは公開のため
  無料枠の消費を気にする必要はほぼない。ただし実行時間＝待ち時間なので乱発しない
- **Claude の実装**: サブスクリプションの利用枠から消費される。枠が切れている間は
  `@claude` への依頼と自動レビューが動かなくなるが、**自動レビューの失敗はワーニング
  止まりでマージ・デプロイは止まらない**（テストが緑なら §2-⑤ の手順でマージできる）
- 節約のコツは 3 つ:
  1. Issue を具体的に書いて**往復回数を減らす**（これが一番効く）
  2. `/apk` は**操作を確認したい PR だけ**で使う（見た目だけなら Web プレビューで足りる）
  3. 細かい修正は 1 つの PR 上で `@claude` コメントを重ねる（Issue を乱発しない）

## 8. 初回だけ: ループの試運転

本格的に使い始める前に、小さな依頼で一周させて全経路の動作を確かめておく。
（先に管理者が [manual_setup/github_automation.md](manual_setup/github_automation.md) の
セットアップを済ませていること）

- [ ] 「改善したいこと」で軽微な文言修正などを Issue にし、「依頼する」を選ぶ
- [ ] 3〜15 分以内に PR が立つ
- [ ] PR にテスト結果（緑）とプレビュー URL がコメントされる
- [ ] プレビューをスマホで開ける（ログインまで通ることを確認）
- [ ] マージすると 25 分以内に本番 URL へ反映される
- [ ] その PR（またはマージ後の PR）に `/apk` とコメントし、App Tester に通知が届く

どこかで詰まったら §6 と [manual_setup/github_automation.md](manual_setup/github_automation.md) の
トラブルシューティングを見る。
