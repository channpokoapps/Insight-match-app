# アカウントと支払いの準備

**すべての作業の一番最初にやること。**
Supabase もドメインも Meta も Google Play も、すべて「どのアカウントで契約したか」に紐づく。
ここを適当に始めると、後から取り返しがつかなくなる。

> このドキュメントは「まだ何も契約していない状態」を前提に書いている。
> すでにアカウントを作ってしまった場合も、**6 章のセキュリティ設定だけは必ず実施する**。

---

## 1. 先に決めること：運営主体（`OI-05`）

【事実】Meta のビジネス認証と Google Play の本人確認は、**「誰がこのサービスを運営しているか」**を証明する手続き。
ここが決まらないと、どちらも申請できない。

| 選択肢 | Meta ビジネス認証 | Play デベロッパー登録 | 難易度 |
| --- | --- | --- | --- |
| 法人 | 登記情報・公開電話番号で認証。**通りやすい** | 組織アカウント。D-U-N-S 番号が必要（取得に 1〜2 週間） | 手続きは多いが確実 |
| 個人事業主 | 開業届の控え・事業用の公開情報で認証。**通ることが多いが要確認** | 個人アカウント。運転免許証等で本人確認 | 中 |
| 個人（開業届なし） | **認証が通らない可能性が高い** | 個人アカウントは可能 | Instagram 連携が成立しない恐れ |

> **【推奨】最低でも個人事業主として開業届を出しておく。**
> Meta のビジネス認証は「実在する事業者であること」を確認する手続きで、
> 完全な個人だと証明する書類がない。
> このアプリは Instagram 連携が成立しないと**サービスとして成り立たない**ため、
> ここは節約する場所ではない。

### 決めたら記録すること

| 項目 | 例 | 使う場面 |
| --- | --- | --- |
| 運営者名 | 屋号または法人名 | 規約、ストア掲載、Meta 認証 |
| 所在地 | 郵便番号・住所 | 規約、特商法表記、Meta 認証 |
| 連絡先メール | `support@（自分のドメイン）` | 規約、ストア、Meta 認証 |
| 電話番号 | 事業用の番号 | Meta 認証（公開情報との突合に使われる） |

これらは legal.md（未執筆）の規約と、google_play.md（未執筆）のストア掲載で必ず必要になる。

## 2. なぜ専用アカウントが必要か

運用に使うアカウントは、**個人用（普段使い）と必ず分ける。**

| 分ける理由 | 分けないと起きること |
| --- | --- |
| 引き継ぎができる | 開発者が離れると、誰も本番環境を触れなくなる |
| 支払いを分離できる | 個人の買い物とクラウドの請求が混ざる |
| 誤操作を防げる | 普段使いのタブから本番プロジェクトを消してしまう |
| 広告の規約を守れる | 個人の閲覧履歴と広告アカウントが混ざり、無効トラフィックを疑われる |

> **【例外】Meta（Facebook）だけは、個人アカウントを新規に作り直さない方がよい。**
> 作りたてのアカウントは審査・認証で不利に扱われることがある。
> **実名で運用している既存の Facebook 個人アカウント**を使い、
> そこから「ビジネスポートフォリオ」を作る形にする（詳細は [meta_instagram.md](meta_instagram.md)）。

## 4. Google アカウントを作る

1. <https://accounts.google.com/signup> を開く。
2. 「**自分用**」を選ぶ。
3. 入力内容の目安:

| 項目 | 入力例 | 注意 |
| --- | --- | --- |
| 姓名 | 実名または屋号 | Play Console の本人確認と一致させると手続きが早い |
| ユーザー名 | `<サービス名>.ops@gmail.com` | **後から変更できない。**個人名を含めない方が引き継ぎやすい |
| パスワード | 20 文字以上のランダム | パスワードマネージャで生成する |

4. 電話番号の確認を行う。
5. 生年月日・性別を入力する（**実際の情報を入れる**。虚偽だとアカウント復旧時に不利になる）。

> **重要: このアカウントを日常のブラウジングに使わない。**
> 自分の広告を自分でクリックしてしまう事故を防ぐため、
> 広告の管理以外で AdMob のアカウントで Web を閲覧しない。

## 5. パスワードマネージャを用意する

これから **15 個以上の資格情報**を管理することになる。メモ帳では必ず事故る。

| ツール | 費用 | 備考 |
| --- | --- | --- |
| Bitwarden | 無料枠あり | オープンソース。個人利用は無料で十分 |
| 1Password | 月 400 円程度 | 使いやすい。チーム共有が容易 |
| ブラウザ内蔵のパスワード管理 | 無料 | **アカウント自体の情報を保存できない**ので単独では不十分 |

### 保管すべき情報

| # | 情報 | 紛失したときの影響 |
| --- | --- | --- |
| 1 | 運用 Google アカウントのパスワード | **Play / Firebase / AdMob をすべて失う** |
| 2 | 2 段階認証のバックアップコード | ログイン不能 |
| 3 | Facebook（Meta）アカウントのパスワード | **Instagram 連携が全停止する** |
| 4 | Supabase のログイン情報 | データベースにアクセスできない |
| 5 | **Supabase のデータベースパスワード** | 直接接続・復旧作業ができない |
| 6 | **Supabase の `service_role` キー** | 漏洩すると全データが読み書きされる |
| 7 | **Meta アプリのアプリシークレット** | 漏洩すると連携を乗っ取られる |
| 8 | **トークン暗号化鍵**（`OI-17`） | **紛失すると保存済みの SNS トークンが全部復号できなくなる** |
| 9 | Android のアップロード鍵（`upload-keystore.jks`）のパスワード | アプリを更新できない |
| 10 | ドメインレジストラのログイン情報 | ドメイン更新不能 → 規約 URL と OAuth が停止 |
| 11 | GitHub アカウントのパスワード・復旧コード | ソースと CI を失う |
| 12 | AdMob アプリ ID / 広告ユニット ID | 再取得は可能 |

> **`upload-keystore.jks` そのもの（ファイル）も忘れずにバックアップする。**
> 詳細は monitoring_backup.md（未執筆）。

### 保管してはいけない場所

| 場所 | 理由 |
| --- | --- |
| リポジトリの中 | 誰でも読める。GitHub が公開設定になった瞬間に終わる |
| Slack / LINE / メール | 検索で出てくる。退職者も読める |
| デスクトップのテキストファイル | PC を盗まれたら終わり |

## 6. 支払い方法を用意する

| 項目 | 内容 |
| --- | --- |
| 必要なもの | クレジットカード（デビットカードは一部サービスで拒否される） |
| 使う場面 | Supabase の月額、ドメイン更新、Play Console 登録料 $25 |
| 名義 | 本人確認書類と一致させる（Play Console / AdMob の審査で照合される） |

### 事故を防ぐ設定

- [ ] カードの有効期限をカレンダーに登録する（**期限切れでドメインが失効すると、規約 URL も OAuth も同時に死ぬ**）
- [ ] カードの利用通知（メール / アプリ通知）をオンにする
- [ ] Supabase の使用量アラートを設定する（monitoring_backup.md（未執筆））

## 7. アカウントを守る設定（必須）

### 7.1 Google アカウント

<https://myaccount.google.com/security> で設定する。

1. 「**2 段階認証プロセス**」→「**使ってみる**」。
2. 電話番号を登録し、SMS で確認する。
3. 有効化後、より安全な方法を追加する。

| 方法 | 安全性 | 備考 |
| --- | --- | --- |
| パスキー | 高 | 端末の生体認証でログイン。**最も推奨** |
| 認証アプリ | 高 | 機種変更のときは移行を忘れない |
| SMS | 中 | 電話番号の乗っ取りに弱い。予備として残す |

4. 「**バックアップ コード**」を取得し、印刷するかパスワードマネージャに保存する。
5. 「**再設定用のメールアドレス / 電話番号**」を登録する。

### 7.2 Facebook（Meta）アカウント

<https://www.facebook.com/settings?tab=security> で設定する。

- [ ] 二段階認証を有効にする（**認証アプリを推奨**。SMS だけにしない）
- [ ] リカバリーコードを保存する
- [ ] 「ログインアラート」を有効にする

> **Meta アカウントを乗っ取られると、アプリの設定を書き換えられ、
> 全ユーザーの Instagram 連携が悪用されうる。** ここは最も厳重に守る。

### 7.3 Supabase アカウント

<https://supabase.com/dashboard/account/security> で設定する。

- [ ] **MFA（多要素認証）を有効にする**
- [ ] 組織の設定で「MFA 必須」にする（複数人運用の場合）

### 7.4 GitHub アカウント

- [ ] 2 要素認証を有効にする
- [ ] リカバリーコードを保存する

## 8. 複数人で運用する場合

一人で全部を持つと、その人が倒れたときにサービスが止まる。
**最低もう一人、管理権限を持つ人を用意する**ことを推奨する。

| サービス | 追加方法 | 付与する権限の目安 |
| --- | --- | --- |
| Supabase | Organization → Team → Invite | 開発者は `Developer`、`Owner` は最小限 |
| Meta ビジネスポートフォリオ | ビジネス設定 → ユーザー → 人 | 「従業員アクセス」。管理者は最小限 |
| Google Play Console | ユーザーと権限 → ユーザーを招待 | 「リリースを表示」から始める |
| Firebase | プロジェクトの設定 → ユーザーと権限 | `編集者`。`オーナー` は配らない |
| GitHub | Settings → Collaborators | `Write`。`Admin` は最小限 |

> **デベロッパーアカウントや Meta のビジネス所有権の移管には手続きが必要**で、簡単ではない。
> 最初にどのアカウントで登録するかを慎重に決める。

### 引き継ぎ用のメモ

以下をまとめた文書を、**リポジトリ外**の安全な場所に置く。

| 項目 | 記載内容 |
| --- | --- |
| 運営主体 | 法人名／屋号、所在地、連絡先 |
| 運用アカウント | 各サービスのログイン ID と、パスワードマネージャ上の保管場所 |
| Supabase | 組織名、プロジェクト ID（本番 / 開発） |
| Meta | ビジネスポートフォリオ ID、アプリ ID |
| ドメイン | レジストラ名、更新月 |
| Play Console | デベロッパー名、登録アカウント |
| 支払い方法 | カードの名義と、更新が必要な時期 |
| 障害時の連絡先 | 誰に連絡すればよいか |
