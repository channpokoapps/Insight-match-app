# ADR-0003: インサイト非開示をスキーマ分離＋RPC＋k-匿名性の 3 層で担保する

- **状態**：承認
- **日付**：2026-07-31
- **関連**：[02_system_overview.md](../requirements/02_system_overview.md) 2-4、[08_data_model.md](../requirements/08_data_model.md)、`NFR-SEC-01`〜`03`、`NFR-SEC-11`

## 背景

要件は次の 3 つを同時に満たす必要がある。

1. PR依頼者はインサイトを**条件として指定できる**。
2. PR依頼者は個々の投稿者の**実数値を一切閲覧できない**。
3. 投稿期間終了後、PR依頼者は**匿名集計された成果**を閲覧できる。

「アプリ側で表示しない」だけでは、API レスポンスに値が含まれていれば通信内容から取得できてしまう。また、条件を少しずつ変えて該当人数の変化を観測すれば、特定個人の値を二分探索で逆算できる。

## 選択肢

| 案 | 概要 | 評価 |
|---|---|---|
| A | アプリ側で表示を制御する | × レスポンスに値が含まれれば漏れる |
| B | API レスポンスから値を除外する（同一スキーマ、RLS のみ） | △ 列単位の遮断は可能だが、実装ミス・将来の改修で漏れやすい |
| C | **スキーマ分離＋`SECURITY DEFINER` RPC＋k-匿名性** | ◎ クライアントから到達する経路が構造的に存在しない |

## 決定

**C** を採用する。3 層で防御する。

### 第 1 層：スキーマ分離（DB 権限）

- インサイト実数値と SNS トークンは `private` スキーマにのみ置く。
- `private` を `anon` / `authenticated` に GRANT せず、PostgREST の公開スキーマにも含めない。
- 結果として、クライアントが SDK から `private.*` をクエリすると**必ず権限エラー**になる。

### 第 2 層：RPC による情報の絞り込み

- `private` を読めるのは `SECURITY DEFINER` 関数と `service_role`（Edge Functions）のみ。
- RPC の戻り値型に実数値を含むフィールドを定義しない。返してよいのは boolean / 件数 / 匿名集計値のみ。
- 関数は `SET search_path = ''` とし、スキーマを完全修飾で書く。

### 第 3 層：出力の丸めと k-匿名性（k = 5）

- 成果レポートは対象人数 n < 5 で非表示。
- 条件設定時の該当人数も 5 未満は実数を返さない（**二分探索攻撃の防止**）。
- ヒストグラムは件数 5 未満のビンを隣接ビンへ統合し、ビン境界は固定値にする。
- PR依頼者に見せる投稿者の識別子は `applications.alias_no`（案件内連番）のみ。

## 結果

- 良い影響：アプリ実装のバグや将来の改修があっても、クライアントに実数値が到達しない。レビュー時のチェック項目が「`private` への経路がないか」という単純な不変条件に還元される。
- 受け入れるトレードオフ：
  - 投稿者本人が自分の値を見る場合も RPC を経由するため、実装がやや冗長になる。**単純な不変条件を保つ価値のほうが大きい**と判断する。
  - 該当人数を丸めるため、PR依頼者は「4 人」なのか「1 人」なのかを知れない。UX より安全性を優先する。
- 新たな制約：
  - `private` の内容を `public` のテーブル・ビュー・マテビューに写像することを**禁止**する。
  - `supabase/tests/` に権限テスト・k-匿名性テストを置き、CI で常時検証する。落ちたらマージ禁止。
  - 将来の有料プランでも「課金すれば実数値が見える」機能を作らない（[12_future_extensions.md](../requirements/12_future_extensions.md) I-2）。
