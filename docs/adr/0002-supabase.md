# ADR-0002: バックエンドに Supabase（PostgreSQL）を採用する

- **状態**：承認
- **日付**：2026-07-31
- **関連**：[11_tech_stack.md](../requirements/11_tech_stack.md) 11-2、`NFR-SEC-01`、`NFR-COST-01`

## 背景

- ランニングコストと運用保守工数の最小化が最優先。初期規模は数十〜数百ユーザー。
- 本アプリの中核制約は「**インサイト実数値をクライアントに絶対到達させない**」こと。
- 投稿者条件は **AND / OR の任意ネスト**で指定でき、該当人数をリアルタイムに返す必要がある。
- 成果レポートで平均・中央値・最小・最大・ヒストグラムを算出する必要がある。
- 案件検索で都道府県・駅・現在地からの距離を扱う必要がある。

## 選択肢

| 案 | 概要 | 長所 | 短所 |
|---|---|---|---|
| A | Supabase（PostgreSQL + RLS + Edge Functions） | スキーマ単位の GRANT で非開示を構造的に強制できる。AND/OR 条件・集計・地理検索が SQL で完結。ロックインが低い | SQL の知識が必要 |
| B | Firebase（Firestore + Cloud Functions） | 初期構築が速い。リアルタイムが強い | **Firestore は OR・複数範囲条件に強い制約**があり条件式が破綻する。集計・中央値・ヒストグラムを自作する必要がある。「このフィールドは絶対返さない」の強制が難しい。読み取り課金が読みにくい |
| C | AWS（Lambda + RDS / Amplify） | 自由度が高い | 構築・運用工数が大きい。RDS は使わなくても課金 |

## 決定

**A（Supabase）** を採用する。

理由は 2 点。

1. **非開示要件との適合性**。「特定のデータをクライアントに絶対到達させない」という制約は、PostgreSQL の**スキーマ単位の GRANT** で構造的に実現できる。Firestore のセキュリティルールは「どのドキュメントを読めるか」の制御であり、フィールド単位の絶対的な遮断には向かない。
2. **条件マッチングと集計**。AND/OR の任意ネスト、`percentile_cont` による中央値、ヒストグラム、地理検索はいずれも SQL の得意分野。

なお **FCM（プッシュ通知）だけは Firebase を併用**する（Supabase に同等機能がなく、無料枠が大きいため）。

## 結果

- 良い影響：非開示要件が DB 権限で担保されるため、アプリ実装のバグで漏れる経路が構造的に存在しない。素の PostgreSQL のため将来の移行余地がある。
- 受け入れるトレードオフ：Free プランはプロジェクト未使用時に一時停止されうる。Edge Function に実行時間上限がある（ADR-0004 で対処）。
- 新たな制約：
  - `public` に新テーブルを作るときは同じマイグレーションで RLS を有効化する。
  - Supabase 固有機能への依存を最小化する（RLS・RPC は PostgreSQL 標準機能）。
