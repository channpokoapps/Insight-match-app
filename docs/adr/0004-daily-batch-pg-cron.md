# ADR-0004: 日次インサイト取得バッチを pg_cron ＋ Edge Function で実行する

- **状態**：承認
- **日付**：2026-07-31
- **関連**：[09_external_integrations.md](../requirements/09_external_integrations.md) 9-7、`FR-INS-01`〜`04`、`NFR-COST-02`

## 背景

- インサイトは 1 日 1 回のバッチで更新する（リアルタイム取得はしない）。
- SNS API にはレート制限があり、スロットリングとリトライが必要。
- 常時稼働サーバーを持たない方針。追加の運用対象を増やしたくない。
- Supabase の Edge Function には実行時間の上限がある。

## 選択肢

| 案 | 概要 | 長所 | 短所 |
|---|---|---|---|
| A | Supabase `pg_cron` ＋ Edge Function | 追加サービス不要・追加コストゼロ。運用対象が増えない。ジョブ状態を同じ DB に持てる | Edge Function の実行時間上限に配慮が必要 |
| B | GitHub Actions の cron | 無料枠が大きくログが見やすい | スケジュールの実行時刻が保証されない。DB 接続情報を CI に持たせる必要がある |
| C | Cloud Run Jobs 等の外部ジョブ基盤 | 実行時間の制約がない | 別サービスの管理・課金が増える |

## 決定

**A（pg_cron ＋ Edge Function）** を採用する。

実行時間上限には**ディスパッチャ＋ワーカー方式**で対処する。

```
pg_cron（日次） → sync-insights（ディスパッチャ）
                    ├─ private.sync_jobs にジョブを作成
                    └─ 対象を N 件ずつのチャンクに分割して sync-worker を起動
                                                     └─ SNS API 呼び出し → private に保存
                                                     └─ 結果を sync_job_items に記録
pg_cron（数時間ごと） → 失敗分の再試行
```

### 初期パラメータ

| 項目 | 値 |
|---|---|
| 実行時刻 | 毎日 03:00 JST |
| 同時実行数 | 5 アカウント |
| 1 アカウントあたりの取得メディア | 直近 90 日・最大 100 件 |
| リトライ | 最大 5 回、指数バックオフ（5分→15分→45分→2時間→6時間） |
| 失敗率アラート閾値 | 10% |

## 結果

- 良い影響：追加コストゼロ。ジョブの状態が DB にあるため、管理画面から実行状況を確認できる。
- 受け入れるトレードオフ：1 回の実行で処理できるアカウント数に上限がある。数千ユーザー規模になったら、ユーザーをハッシュで分散し「全員を毎日更新しない」方式へ移行する。
- 新たな制約：
  - **1 アカウントの失敗が他アカウントを止めない。** ユーザー単位で例外を捕捉して `sync_job_items` に記録する。
  - 認可エラーはリトライせず `reauth_required` に遷移させ、投稿者へ通知する。
  - YouTube 対応時はプロジェクト単位のクォータ（10,000/日）を消費量として記録し、上限の 80% で打ち切って翌日へ繰り越す。
